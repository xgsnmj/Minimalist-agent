# 简洁明确的中文代码注释规范

Minimalist Agent 的代码注释默认使用简体中文。注释的任务不是重复代码，而是帮后续维护者快速理解这里为什么这样写、这里保证什么、以及有哪些不容易从实现本身直接看出的边界。

## Decision

1. 默认使用简体中文注释。
2. 注释只解释代码无法直接表达的信息，不重复字面意思。
3. 只在这些场景写注释：
   - 非显然的业务规则、状态转换、不变量。
   - 为什么选择当前实现，而不是另一个看起来也能工作的方案。
   - 临时兼容、迁移期 shim、历史包袱、workaround。
   - 复杂分支、边界条件、并发、性能或安全约束。
   - seam 边界上的输入假设、输出保证和副作用。
4. 不写这些内容：
   - 代码本身已经说清楚的逻辑。
   - 变量名、函数名、类型名已经表达出来的信息。
   - 重复接口文案、重复测试名、重复提交说明。
5. 注释要短，优先一两句，避免长篇解释。
6. 注释要贴近被解释的代码；复杂模块可先写块注释，再在关键行补一句。
7. 公开 API 可写 docstring，但内部实现优先用更近的行内或块注释。
8. 注释里的专有名词、函数名、类型名可以保留英文，其余说明用中文。

## 写法

- 优先写“为什么”和“保证什么”，少写“是什么”。
- 句子尽量具体，不写空话。
- 能说清约束就说约束，能说清前提就说前提。
- 如果一段代码因为太绕才需要一长串注释，先考虑抽函数或拆模块。

## 例子

好的注释：

```ts
// 这里必须先冻结快照，再启动 run，避免用户修改后读到不一致的配置。
```

```py
# 这里保留旧字段是为了兼容迁移窗口，等所有客户端切到新字段后再删除。
```

不好的注释：

```ts
// 初始化 run
```

```py
# 遍历列表
```

## Consequences

- 维护者更容易理解代码意图和边界。
- 注释会更少，但更有信息量。
- 写代码时需要多想一步：这句到底是在解释，还是在重复实现。
